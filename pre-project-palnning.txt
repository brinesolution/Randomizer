================================================================================
1. PROJECT MOTIVATION
================================================================================

Problem:
Computers are deterministic. Pure software cannot generate truly random numbers from nothing. Normal pseudo-random number generators produce sequences from algorithms and seeds. If the seed and internal state are known, future outputs may be predictable. In security-sensitive systems, weak randomness can cause severe vulnerabilities such as predictable OTPs, weak session tokens, poor cryptographic keys, and authentication failures.

Project motivation:
The aim is to study randomness as a real engineering pipeline:
1. collect noisy physical or hardware-derived signals,
2. extract entropy-like raw bytes,
3. test whether sources look healthy,
4. fuse several independent-ish sources,
5. condition the fused entropy using standard cryptographic hash functions,
6. generate a clean 6-digit OTP using unbiased mapping,
7. log all runs with source metrics,
8. build a dataset,
9. use statistical tests and ML models to attempt prediction,
10. evaluate whether the OTP generator is weak, biased, or hard to predict.

Important framing:
Do not claim this is a certified cryptographic TRNG. It is a research/portfolio prototype for entropy collection and evaluation.

Correct framing:
"A laptop-only multi-source entropy fusion system that collects hardware-derived noise signals, conditions them, generates 6-digit OTPs, and evaluates predictability statistically and using ML."

Incorrect framing:
"I invented a perfect true random number generator."
"This replaces Google Authenticator or bank OTP systems."
"This is guaranteed cryptographically secure."

Portfolio reason:
This project combines:

2. MAJOR CONCEPTS DISCUSSED
================================================================================

2.1 Why computers cannot generate true randomness using pure software

Pure software is deterministic:
Input + instructions + state = output.
If all inputs and state are repeated, the result repeats.
This is why normal software random number generators are pseudo-random.

True randomness requires a physical entropy source, such as electrical noise, radioactive decay, sensor noise, thermal noise, quantum effects, camera noise, microphone ADC noise, or timing jitter.

2.2 Hardware-assisted randomness

A stronger system collects noise from real physical processes, such as:
- diode electrical noise,
- camera sensor dark-frame noise,
- microphone analog-to-digital noise,
- CPU timing jitter,
- OS scheduler jitter,
- human input timing,
- external sensor fluctuations.

For this project, the user currently wants a laptop-only prototype, so no diode hardware in the base implementation.

2.3 Laptop-only entropy sources selected

Accepted laptop-only entropy sources:
1. Camera dark-frame noise
2. Microphone ADC noise
3. CPU timing jitter
4. OS scheduler/thread timing jitter

Rejected for base project:
1. Mouse/touchpad/keyboard timing, because it requires human intervention and the user wants automated 10,000-run generation.
2. Direct laptop motherboard electrical noise, because normal software cannot directly access raw analog electrical noise from the motherboard.
3. Diode electrical noise in base project, because the current base project should be laptop-only. It remains a future extension.
4. OS randomness as the core entropy source, because that would mostly be calling the operating system's existing RNG rather than building our own entropy pipeline. It can be used as a baseline comparison only.
5. Network timing as a core source, because it depends on router/internet conditions and is not reliable offline.
6. Battery/temperature sensors as core sources, because they are often slow, low-resolution, and not sufficiently variable.
7. Disk I/O timing as a core source, because it can be affected by caching and may create unnecessary SSD wear if used aggressively. It can be optional/future.

2.4 OTP generation concept

The user initially proposed:
- generate random outputs multiple times,
- one run gives 3 digits, another gives 2 digits, another gives 1 digit,
- concatenate chunks until a 6-digit OTP is produced.

Rejected as primary method:
Variable-length digit stitching can introduce bias or uneven digit distribution unless handled very carefully.

Accepted method:
Generate one uniform integer in range 0 to 999999 and format it as a 6-digit OTP with leading zeros.

Example:
42 -> 000042
9182 -> 009182
762341 -> 762341

Recommended method:
Use rejection sampling from a hash digest / generated random block to avoid modulo bias.

2.5 ML evaluation concept

Stage 2 of the project should try to break the generator.
The user wants to generate 10,000 OTP samples and use ML/statistical models to see if the OTP can be predicted from source metrics, previous OTPs, timestamps, or experimental values.

Accepted ML goals:
1. Predict each OTP digit individually.
2. Predict next OTP digit from previous OTP sequence and features.
3. Predict OTP bucket/range.
4. Detect correlations between source features and output digits.
5. Compare ML accuracy to random baseline.
6. Run anomaly detection for source health.

Rejected or deprioritized ML goal:
Predict full 6-digit OTP as a 1,000,000-class classification problem using only 10,000 samples. This is not useful as a main task because the output space is much larger than the dataset. It can be included as a sanity check only.

3. BASE PROJECT SCOPE
================================================================================

The base project should include:

1. Four laptop-only entropy sources:
   - camera dark-frame noise,
   - microphone ADC noise,
   - CPU timing jitter,
   - OS scheduler/thread timing jitter.

2. Independent source modules:
   Each source must be implemented in its own file/class with a standard interface.

3. Parallel/decentralized collection:
   Sources should be collected concurrently where possible. The central manager should call each source independently and gather raw blocks.

4. Health tests:
   Before mixing, each source should be checked for basic failure or bad quality.

5. Source-level feature extraction:
   Store metrics per source:
   - byte count,
   - bit balance,
   - entropy estimate,
   - mean/std for timing sources,
   - autocorrelation estimate,
   - health pass/fail,
   - collection time.

6. Multi-source fusion algorithm:
   Recommended named algorithm:
   HG-MSEF = Health-Gated Multi-Source Entropy Fusion.

7. Cryptographic conditioning:
   Use SHA-512 or BLAKE2b from Python hashlib.
   Do not invent a new cryptographic hash function.

8. OTP generation:
   Generate one uniform integer in [0, 999999] using rejection sampling.
   Format as 6 digits with leading zeros.

9. Dataset logging:
   Log every run into CSV/Parquet/JSONL.
   Keep public metadata separate from private raw entropy data.

10. Automated generation:
   Run at least 10,000 times.

11. Statistical analysis:
   Analyze digit frequency, OTP distribution, collision count, autocorrelation, entropy estimates, chi-square tests, and source-output correlation.

12. ML attack phase:
   Train models to predict digits or next digits and compare accuracy to random baseline.

13. Documentation:
   README, architecture diagram, algorithm documentation, limitations, experiment report.

4. ACCEPTED ENTROPY SOURCES FOR BASE PROJECT
================================================================================

Source 1: Camera dark-frame noise
Formal name:
Optical Sensor Dark-Frame Noise Source

Purpose:
Collect physical/electronic noise from the laptop webcam sensor.

Method:
1. Use OpenCV to access webcam.
2. Ask user to cover camera physically before running long experiments.
3. Capture one or more frames per OTP generation run.
4. Convert frame to grayscale.
5. Extract least significant bits from pixel values.
6. Optionally compute frame differences between consecutive frames.
7. Convert extracted LSBs / deltas to raw bytes.
8. Hash source block before mixing.

Notes:
- Camera noise depends on exposure, lighting, resolution, sensor behavior, compression, driver settings.
- Fixed settings improve reproducibility.
- If auto-exposure changes too much, source behavior may change.
- Store camera metadata: frame size, mean pixel value, std pixel value, LSB balance.

Possible OpenCV package:
opencv-python

Source 2: Microphone ADC noise
Formal name:
Audio ADC Noise Source

Purpose:
Collect analog-to-digital noise from microphone input and background signal variations.

Method:
1. Use sounddevice or PyAudio to record a short audio block.
2. Prefer quiet environment.
3. Disable noise suppression if possible, but this may not be easy through Python.
4. Extract low-order bits from PCM samples.
5. Use sample deltas or LSBs as raw noise bytes.
6. Run health tests to detect muted/constant microphone.

Notes:
- External sound can influence microphone data.
- Microphone can be muted, permission-blocked, or processed by OS noise cancellation.
- It is useful but should not be trusted alone.

Possible Python packages:
sounddevice
numpy

Source 3: CPU timing jitter
Formal name:
Processor Timing Jitter Source

Purpose:
Collect timing variability from repeated CPU operations.

Method:
1. Use time.perf_counter_ns() for high-resolution timing.
2. Run small deterministic CPU operations repeatedly.
3. Measure delta times between iterations.
4. Extract low-order bits of timing deltas.
5. Hash result before mixing.

Notes:
- Python is not ideal for ultra-low-level timing, but sufficient for experimental project.
- Source may be affected by CPU load, power settings, background processes, interpreter overhead, OS scheduling.
- This source is still useful for a laptop-only prototype.

Source 4: OS scheduler/thread timing jitter
Formal name:
OS Scheduler and Thread Timing Jitter Source

Purpose:
Collect timing variation caused by scheduling, context switching, interrupts, background system activity, and thread yield behavior.

Method:
1. Use several worker threads.
2. Each worker records perf_counter_ns() deltas.
3. Each worker calls time.sleep(0) or performs small yields.
4. Collect low-order timing delta bits.
5. Hash result before mixing.

Notes:
- Similar to CPU jitter but conceptually distinct: this source focuses on OS scheduling behavior, thread timing, and context switches.
- Fully automated and suitable for 10,000-run generation.

5. REJECTED / DEFERRED SOURCES AND WHY
================================================================================

Rejected for base project: Mouse/touchpad/keyboard timing
Reason:
Requires human input. Not suitable for automated 10,000-run dataset generation.
Future use:
Could be added as an optional interactive entropy source for manual demo mode.

Rejected for base project: Diode electrical noise
Reason:
Requires external hardware. User currently wants laptop-only version.
Future use:
Strong future upgrade. Add Arduino/Pico/ESP32 + diode noise circuit and compare laptop-only vs diode-assisted entropy.

Rejected for base project: Direct laptop electrical noise measurement
Reason:
Normal software cannot directly access analog motherboard electrical noise.
Future use:
Would require external ADC, oscilloscope, microcontroller, or custom hardware taps. Not feasible safely/software-only.

Rejected as main source: OS randomness / Python secrets / os.urandom
Reason:
Using it as the source would reduce the project to calling the existing OS RNG. It is good as a baseline comparison only.
Usage:
Include as baseline in experiments:
- compare digit distribution,
- compare generation speed,
- compare ML predictability.

Rejected as core source: Network timing
Reason:
Depends on internet/router/server conditions. Not reproducible. Not ideal offline.
Future use:
Optional environmental entropy source in advanced version.

Rejected as core source: Battery/temperature sensor readings
Reason:
Low resolution, slow, often inaccessible or too stable.
Future use:
Optional metadata feature, not entropy source.

Rejected as core source: Disk I/O timing
Reason:
Affected by caching and can create unnecessary disk writes. Reads may be too deterministic. SSD wear concerns if abused.
Future use:
Optional fifth automated source using memory-mapped temp files or read timing only, with care.

Rejected method: Variable-length OTP chunk stitching
Reason:
Can introduce bias and complicates correctness.
Accepted alternative:
Generate full OTP using uniform integer mapping from conditioned random block.

Rejected method: Output raw sensor bits directly
Reason:
Raw noise may be biased, correlated, or source-dependent.
Accepted alternative:
Health test raw bits, then cryptographically condition with SHA-512/BLAKE2b.

Rejected method: Simple modulo only
Reason:
Modulo reduction can introduce tiny bias if source range is not a multiple of 1,000,000.
Accepted alternative:
Use rejection sampling. For prototype modulo from 512-bit digest has negligible practical bias, but rejection sampling is cleaner and more defensible.

Rejected claim: Certified true random generator
Reason:
No formal certification or deep entropy-source validation.
Accepted claim:
Laptop-only hardware-derived entropy OTP generator with statistical and ML-based evaluation.

6. MODERN DECENTRALIZED ARCHITECTURE
================================================================================

Design principle:
Each source should work independently in its own module. A central orchestrator/manager calls all sources, preferably in parallel, collects raw blocks and metrics, and sends them to the health gate, mixer, OTP generator, and logger.

Architecture style:
- Source modules are decentralized.
- Manager is centralized only for orchestration.
- Fusion algorithm is separate.
- Health tests are separate.
- Data logging is separate.
- ML and analysis are separate from production generation.

High-level pipeline:

[Source Workers]
   camera_source.py
   microphone_source.py
   cpu_jitter_source.py
   scheduler_jitter_source.py
        ↓
[Entropy Manager]
   entropy_manager.py
        ↓
[Health Gate]
   health_tests.py
        ↓
[Feature Extractor]
   features.py
        ↓
[Source Hasher]
   source_hasher.py
        ↓
[Multi-Source Fusion]
   hg_msef.py
        ↓
[Conditioner]
   conditioner.py
        ↓
[OTP Generator]
   otp.py
        ↓
[Experiment Logger]
   run_logger.py
        ↓
[Dataset + Analysis + ML Attack]

Concurrency model options:

Option A: ThreadPoolExecutor
Good for camera/mic/timing sources. Simpler than async for mixed blocking libraries.

Option B: multiprocessing
Useful if CPU jitter/scheduler jitter should avoid GIL interference, but adds complexity.

Option C: asyncio
Useful for API service, not necessarily for camera/audio capture.

Recommended for MVP:
Use concurrent.futures.ThreadPoolExecutor for source collection.

Recommended for advanced version:
Use a hybrid:
- ThreadPoolExecutor for camera/audio/scheduler collection,
- optional multiprocessing for timing-sensitive jitter collection,
- FastAPI async endpoints for API service.

9. SOURCE IMPLEMENTATION DETAILS

9.1 Camera source

File:
src/randomiser/sources/camera_source.py

Dependencies:
opencv-python
numpy

Implementation plan:
1. Open default camera using cv2.VideoCapture(camera_index).
2. Set fixed resolution from config.
3. Optional warmup frames to allow sensor stabilization.
4. Capture N frames.
5. Convert to grayscale.
6. Use one or multiple extraction strategies:
   a. LSB extraction from pixel values.
   b. Difference between consecutive frames.
   c. LSB extraction from frame-delta values.
7. Convert bit array to bytes.
8. Return SourceSample.

Recommended config:
camera:
  enabled: true
  camera_index: 0
  frames_per_run: 2
  width: 320
  height: 240
  warmup_frames: 3
  extract_mode: "frame_delta_lsb"
  target_bytes: 2048

Health metrics:
- frame_mean
- frame_std
- delta_mean
- delta_std
- lsb_ones_ratio
- raw_byte_count
- camera_available

Failure detection:
- camera not available,
- all frames identical,
- near-zero variance,
- too few bytes,
- bit balance extremely skewed.

9.2 Microphone source

File:
src/randomiser/sources/microphone_source.py

Dependencies:
sounddevice
numpy

Implementation plan:
1. Record short audio window, e.g. 50-100 ms.
2. Use sample rate 16000 or 44100.
3. Convert float samples to int16 if needed.
4. Extract LSBs from int16 samples or sample deltas.
5. Convert to bytes.
6. Return SourceSample.

Recommended config:
microphone:
  enabled: true
  sample_rate: 16000
  duration_ms: 80
  channels: 1
  extract_mode: "sample_delta_lsb"
  target_bytes: 2048

Health metrics:
- audio_mean
- audio_std
- zero_sample_ratio
- clipping_ratio
- lsb_ones_ratio
- sample_count

Failure detection:
- microphone permission denied,

================================================================================
10. HEALTH TESTS
================================================================================

The health tests are not meant to prove randomness. They are meant to detect obvious source failures.

Recommended tests:

1. Repetition count test
Detects long repeated byte or bit values.
If too many repeated bytes occur in a row, fail or warn.

2. Frequency / bit balance test
Compute ratio of 1 bits to total bits.
Expected rough range can be broad for raw sources, e.g. 0.35 to 0.65 for warning, 0.20 to 0.80 for hard fail, depending on source.
Do not set too strict thresholds before conditioning.

3. Runs test
Checks whether bits alternate or repeat too unusually.

4. Autocorrelation lag-1
Checks dependency between adjacent bytes/bits.

5. Unique byte count
If only a few byte values appear, source may be weak.

6. Source-specific tests
Camera:
- frame variance > threshold,
- consecutive frames not identical.
Microphone:
- non-zero audio std,
- not clipped,
- not all zeros.
CPU/scheduler:
- enough unique timing deltas,
- std above threshold.

Health gate policy:
- If a source hard-fails, exclude it from fusion.
- If a source warns but does not fail, include it with warning.
- If fewer than min_required_sources pass, mark run as degraded or failed.

Recommended min_required_sources:
- For MVP: 2 of 4
- For best dataset: 3 of 4

================================================================================
12. MULTI-SOURCE FUSION ALGORITHM
================================================================================

Recommended algorithm name:
HG-MSEF: Health-Gated Multi-Source Entropy Fusion

Goal:
Combine multiple entropy source blocks in a safe, explainable, and modular way.

Rules:
1. Do not directly output raw source bytes.
2. Do not trust a source until health checks are done.
3. Do not invent a cryptographic hash function.
4. Use standard hash functions such as SHA-512 or BLAKE2b.
5. Use domain separation labels to avoid ambiguous concatenation.
6. Include run_id and timestamp as metadata, but do not rely on timestamp as entropy.
7. Hash each source independently first.
8. Hash all source digests together to get final digest.
9. Use final digest for OTP generation.

Pseudo-algorithm:

Input:
- run_id
- timestamp_ns
- source_samples: list[SourceSample]
- source_features: dict
- health_results: dict

Steps:
1. healthy_sources = []
2. For each source:
   a. run health tests
   b. extract features
   c. if health passed: include source
   d. else: log failure and exclude
3. if len(healthy_sources) < min_required_sources:
   a. mark run as failed or degraded
   b. optionally retry collection
4. For each healthy source:
   source_digest = HASH(
      "RANDOMISER-SOURCE-v1" ||
      source_name ||
      raw_byte_length ||
      raw_bytes ||
      source_feature_summary ||
      source_collection_timing
   )
5. final_digest = HASH(
      "RANDOMISER-HG-MSEF-v1" ||
      run_id ||
      timestamp_ns ||
      config_hash ||
      sorted(source_digest entries by source_name)
   )
6. Return final_digest and metadata.

Recommended hash:
- hashlib.blake2b(digest_size=64)
or
- hashlib.sha512()

BLAKE2b advantage:
- fast,
- built into Python hashlib,
- supports personalization/keying options if needed.

SHA-512 advantage:
- widely recognized,
- easy to explain.

Recommended for first version:
SHA-512.

Alternative mixers for comparison experiments:
1. Concat + SHA-512
2. Per-source SHA-512 + final SHA-512
3. XOR source digests + SHA-512
4. Health-gated hash mixer (main)

Do not use XOR-only as final method. It can be an experiment.

================================================================================
13. OTP GENERATION METHOD
================================================================================

Requirement:
Generate a uniform 6-digit OTP from 000000 to 999999.

Accepted method:
Use rejection sampling.

Reason:
Avoid modulo bias and make the method defensible.

Algorithm:
1. Input final digest from fusion.
2. Generate 32-bit candidate values by hashing digest + counter.
3. Let M = 1,000,000.
4. Let LIMIT = floor(2^32 / M) * M.
5. If candidate < LIMIT, OTP = candidate % M.
6. Else increment counter and retry.
7. Format OTP as six digits with leading zeros.

Pseudo-code:

def otp_from_digest(digest):
    M = 1_000_000
    LIMIT = (2**32 // M) * M
    counter = 0
    while True:
        block = sha256(digest + counter_bytes).digest()
        value = int.from_bytes(block[:4], "big")
        if value < LIMIT:
            otp_int = value % M
            return f"{otp_int:06d}"
        counter += 1

Rejected method:
Using multiple variable-length random fragments to stitch together six digits.
Reason:
Can introduce bias and is harder to test.

Optional output types for expansion:
- OTP digits: 4, 6, 8
- random integer in a range
- random bytes
- token hex
- dice rolls
- password generator

16. STATISTICAL ANALYSIS PLAN
================================================================================

Minimum analysis:
1. Digit frequency for each position.
2. Overall digit frequency 0-9.
3. OTP collision count.
4. Duplicate rate comparison to expected birthday-collision behavior.
5. Last digit distribution.
6. First digit distribution, remembering leading zeros are valid.
7. Chi-square test for digit uniformity.
8. Autocorrelation between sequential OTPs.
9. Correlation between timestamp/run_id and OTP value.
10. Correlation between source features and OTP digits.
11. Source health failure summary.
12. Generation time distribution.

Important fact:
There are 1,000,000 possible six-digit OTPs.
10,000 samples cover only about 1% of the output space.
Duplicates are expected.
Expected duplicate pairs for 10,000 draws from 1,000,000 values:
about 10,000 * 9,999 / (2 * 1,000,000) ≈ 50.
So duplicates do not automatically mean failure.

Good signs:
- digit prediction accuracy near 10%,
- full OTP prediction near random,
- low correlation with source metrics,
- digit frequencies approximately uniform,
- no obvious sequential trend,
- health checks catch intentionally bad source states.

Bad signs:
- one digit appears much more often,
- a position has strong bias,
- OTP correlates with timestamp/run_id,
- next OTP is easier to predict from previous OTPs,
- ML digit accuracy significantly above 10%,
- source failure causes repeated or biased OTPs.

I wanted to understand how systems collect and validate entropy, so I created a laptop-only multi-source entropy pipeline using camera sensor noise, microphone ADC noise, CPU timing jitter, and scheduler timing jitter. The system health-checks each source, fuses healthy sources using a hash-based mixer, generates six-digit OTPs using unbiased rejection sampling, logs 10,000 runs, and then uses statistics and ML models to test whether outputs are predictable.

What to say if asked "Is it truly random?":
I would describe it as a hardware-derived entropy prototype, not a certified true random generator. The project collects physical and system-level noise sources and evaluates them statistically, but I avoid claiming perfect randomness. The focus is on engineering the entropy pipeline and testing for detectable predictability.

What to say if asked "Why not just use Python random?":
Python's random module is deterministic and not suitable for security. Python's secrets module and OS randomness are better for production. My project is not meant to replace them; it is meant to understand entropy collection, conditioning, and validation underneath.

36. LIMITATIONS TO DOCUMENT
================================================================================

1. Laptop-only sources are not equivalent to direct physical electrical noise from a dedicated TRNG circuit.
2. Camera and microphone data can be affected by OS drivers and preprocessing.
3. CPU and scheduler jitter are affected by system load and Python interpreter behavior.
4. Hashing conditions entropy but does not create entropy from nothing.
5. Passing statistical tests does not prove cryptographic security.
6. 10,000 OTPs are useful for analysis but not enough to exhaustively test a 1,000,000-value OTP space.
7. This is not certified under NIST/FIPS or any formal standard.
8. This should not be used for production authentication.
9. Raw entropy and OTP outputs should not be stored together in production systems.
10. ML failing to predict does not prove security; it only means tested models did not detect exploitable patterns.
